# metrics-lib v2.0.0 — Correct Output, Bounded Registry

metrics-lib 2.0 is a correctness release. An audit of 1.0.0 found that the
Prometheus and OpenMetrics output was invalid in common cases, memory was
reported 1024× too high on Windows and macOS, the token bucket stopped
refilling after 49.7 days, and registries could grow without bound from
unvalidated names. Those bugs were frozen into the 1.0 API, so fixing them
takes a major version. 2.0 also adds what the audit found missing: a
`metrics`-crate recorder, request middleware, a hardened HTTP endpoint,
summaries, exemplars and standard process metrics. An independent re-audit
of the release candidate was addressed before release.

```toml
[dependencies]
metrics-lib = "2"
```

## Highlights

- **Exposition that scrapers accept.** Every exporter's output is parsed by
  strict Prometheus and OpenMetrics validators in the test suite, including
  a property test over 2,048 random registries per run; an independent
  validator found no invalid output in 3,000 more.
- **A bounded, validated registry.** Names and labels are validated or
  repaired, one name holds one kind, the series cap covers every series,
  and idle series can be evicted.
- **Drop-in for `metrics` users.** The `metrics-rs` feature installs
  metrics-lib as the `metrics` recorder, so existing `metrics::counter!`
  call sites, including those in dependencies, record into it.
- **From instrumentation to `/metrics` in one crate.** `tower` middleware
  for request rate, errors and duration, a dependency-free `MetricsServer`
  that a slow or idle client cannot stall, a Pushgateway client, and the
  standard `process_*` series.
- **System metrics without `sysinfo` on the main platforms.** Linux,
  Windows and macOS are read directly: a process sample takes under a
  microsecond on Windows instead of about 30 ms, and the default features
  no longer pull 20 crates into Windows builds. `sysinfo` remains only for
  targets without an in-house backend, such as FreeBSD.
- **Honest numbers.** Every figure in the docs comes from code in the
  repository, with the machine named; `tools/compare-1x` reproduces the
  comparison with 1.0.0. The 1.x claim of a 1.5 ns counter is withdrawn.

## Added

- `init_with_config(MetricsConfig)` and `try_metrics()`; `MetricsConfig`
  with the series cap, system sampling interval, health thresholds and
  eager or lazy system monitoring.
- `UpDownCounter`, `ShardedCounter` for contended counters, and `Summary`
  with streaming quantiles at 2 % relative error.
- Histogram exemplars, emitted in OpenMetrics; the `tracing` feature fills
  them from the current span. They are kept apart from the bucket counts
  (`HistogramSnapshot::exemplars`), so histograms without exemplars pay
  nothing for them.
- `Timer::start_owned` and `MetricsCore::start_timer`, guards that own
  their handle and are `#[must_use]`.
- `ProcessCollector` and `render_with_process` / `render_core`:
  `process_cpu_seconds_total`, `process_resident_memory_bytes`,
  `process_open_fds` and the rest of the standard set.
- Features `metrics-rs` (`MetricsLibRecorder`), `tower` (`RedLayer`) and
  `http` (`MetricsServer`, `Pushgateway`).
- OTLP delta temporality and protobuf encoding; StatsD counter deltas.
- `Registry::remove`, `remove_series`, `evict_idle`, `kind_of` and the
  `try_*` lookups for unlabeled metrics.
- Global shorthand macros: `counter!`, `gauge!`, `histogram!`, `timer!`,
  `summary!`, `up_down_counter!`, `rate!`, `labels!`.

## Changed

- MSRV 1.85 and edition 2024 (was 1.70 and 2021).
- License `Apache-2.0 OR MIT` (was Apache-2.0).
- `MetricsCore::new()` no longer starts a thread; the system monitor
  starts on first use of `system()`, behind the default `system` feature.
- Registry methods lose the `get_or_create_` prefix; the old names remain
  as deprecated aliases.
- Timers export as summaries, rate meters as a `_total` counter plus a
  `_per_second` gauge, dotted names with `_`.
- `RateMeter` is a sliding-window estimate on the monotonic clock that
  honours its window; `TokenBucket` is a GCRA limiter with `u64`
  capacities.
- Public enums and option structs are `#[non_exhaustive]`.
- `system` reads the OS directly on Linux, Windows and macOS; `sysinfo`
  (0.29 to 0.36.1) is compiled only for other targets. `parking_lot` and
  `num_cpus` dropped; the lockfile is current within the MSRV.

## Deprecated

- `Registry::get_or_create_*` and friends. Use the short names:

  ```rust
  let registry = metrics_lib::Registry::new();
  registry.counter("jobs").inc(); // was get_or_create_counter("jobs")
  ```

## Removed

- `MetricsError::Overloaded`, `OverLimit`, `NotInitialized` (never
  produced); `CounterStats::total`, `GaugeStats::updates`,
  `RateStats::window_fill`; `timer::utils::benchmark`; the `bench-tests`
  feature.

## Fixed

- Invalid Prometheus/OpenMetrics output: cross-type name clashes, timers
  typed `histogram` without buckets, malformed rate families, `_total`
  handling, units, missing `# EOF`. StatsD and OTLP also skip clashing
  derived names now (`t` timer versus `t.count` counter).
- Memory 1024× too high on Windows and macOS.
- Linux CPU usage averaged since boot instead of between samples, and
  ignored iowait, irq and steal time.
- `TokenBucket` stopped refilling after about 49.7 days of uptime.
- `ThroughputMeter::record_bytes` truncated values above 4 GiB.
- Concurrent first registration leaked series-cap slots, and
  `Registry::clear` racing with registrations could let the cap drift.
- OTLP cumulative points reset their start time on every export, and did
  not start a new series after a metric was reset.
- `/proc/self/stat` parsing failed for process names containing spaces or
  `)`.
- NaN stuck in gauges after `set_max`, `set_min` or `update_ema`; a timer
  read during its first recording could report a 584-year minimum.
- Panics reachable from public methods (`Gauge::clamp`, empty bucket lists,
  zero sampling rates, failed thread spawn).
- Time-based samplers on one thread shared state; histogram snapshots
  could be non-monotonic under concurrent writes; negative StatsD gauges
  were sent as decrements; JSON wrote `+Inf` bounds as `null`.
- `RedLayer` did not time work done inside the inner `call`, and a panic
  there left the in-flight gauge raised.

The CHANGELOG maps every finding of both audits (ML-001 to ML-038 and
ML2-001 to ML2-018) to its fix.

## Security

- Metric names, label keys and label values can no longer inject lines
  into Prometheus, OpenMetrics or StatsD output.
- Every collection that grows with input is capped, including unlabeled
  names and metadata.
- `MetricsServer` serves each connection on its own thread (at most 16 at
  once), with total deadlines for the request head (2 s, then 408) and the
  response (10 s), and a head limit (8 KiB, then 431). When all 16 slots
  are taken, a new connection evicts one that has not sent its request
  yet, the oldest of the address holding the most such connections, so
  idle connections cannot lock scrapers out and a flooding client evicts
  its own connections first. Clients behind the same address as an
  attacker are not told apart. The
  Pushgateway client enforces one deadline over the whole request and
  splits it fairly across the addresses a host name resolves to.
- `#![deny(unsafe_code)]`. The only `unsafe` code is the OS calls of the
  Windows and macOS system backends: every block has a `SAFETY` comment,
  every FFI struct layout is checked at compile time, every return code is
  checked, and the one kernel resource held (the macOS host port) is
  released by a `Drop` guard. CI compares their readings with `sysinfo`'s
  on Windows and macOS runners.

## Breaking changes

The full list, with replacements, is in
[`docs/MIGRATION-2.0.md`](../MIGRATION-2.0.md). The ones most programs
meet:

### Names are validated and one name holds one kind

```rust
use metrics_lib::{MetricsCore, MetricsError};

let core = MetricsCore::new();
core.counter("requests").inc();
// 1.x silently created an unrelated gauge with the same name.
assert!(matches!(core.try_gauge("requests"), Err(MetricsError::KindMismatch { .. })));
```

### Timers held from a temporary

```rust
let core = metrics_lib::MetricsCore::new();
// 1.x: `core.timer("db").start()` on a temporary failed with E0716.
let _guard = core.timer("db").start_owned();
```

### Exposition names

Timers are now summaries (`t_sum`, `t_count`, plus `t_min`/`t_max`
gauges), rate meters a `r_total` counter and a `r_per_second` gauge, and
dots in names become underscores. Dashboards querying the 1.x names need
updating.

## Performance

Reference machine: AMD Ryzen 9 9950X3D, Windows 11, shared with other
builds. The table is from `tools/compare-1x`, which links 1.0.0 and 2.0.0
into one binary and reports the minimum of 180 interleaved rounds per
operation (rustc 1.95, fat LTO). Full tables, including the Criterion
medians, in [`docs/PERFORMANCE.md`](../PERFORMANCE.md).

| Operation | 1.0.0 | 2.0.0 | Change |
|---|---|---|---|
| `Counter::inc` | 3.85 ns | 3.90 ns | +1 % |
| `Timer::record_ns` | 7.67 ns | 7.63 ns | −1 % |
| `Histogram::observe` | 12.50 ns | 12.56 ns | +1 % |
| Labeled lookup + `inc` | 97.8 ns | 57.2 ns | −42 % |
| Unlabeled lookup + `inc` | 26.5 ns | 28.6 ns | +8 % |
| `Histogram::snapshot` | 48.7 ns | 51.0 ns | +5 % |
| `RateMeter::tick` | 36.5 ns | 41.2 ns | +13 % |
| `RateMeter::rate` | 22.6 ns | 31.8 ns | +41 % |

The regressions above 5 % and why they are accepted:

- **Unlabeled lookup, +2 ns.** Names are routed to one of 16 shards and
  looked up in one map of families of every kind, and the kind of the
  stored series is checked. That is what bounds the registry, refuses a
  second kind under one name and allows eviction. Held handles skip the
  lookup (4 ns per increment).
- **`RateMeter`, +5 ns per tick, +9 ns per `rate()`.** The meter reads the
  monotonic clock instead of the wall clock (1.x broke on NTP steps),
  keeps `u64` second, minute and hour windows instead of `u32` ones, and
  computes a sliding estimate instead of "events since the start of this
  second" (which let `tick_if_under_limit` admit twice its limit). Both
  paths are division-free.

Contention: with eight threads incrementing one counter, a `ShardedCounter`
finishes 5 to 9 times sooner than a `Counter` (Criterion, several runs);
`Counter` itself is as fast as in 1.0.

Exposition: 400 series render in 0.14 ms, and 0.15 ms with the
`process_*` families (`render_core`). A process sample takes 0.66 µs on
Windows; through `sysinfo` it took 31 ms on the reference host (up to
500 ms under heavy load), because `sysinfo` scans every process to refresh
one. A full host-and-process update takes 0.14–0.27 ms (host-dependent)
instead of about 32 ms.

## Platforms

| Platform | System metrics backend | Verified |
|---|---|---|
| Linux (x86_64) | `/proc` | tests run in CI (stable and MSRV) and locally |
| Windows (x86_64) | kernel32 | tests run in CI and locally; values checked against the OS and `sysinfo` |
| macOS (arm64) | libSystem | tests run in CI, including parity with `sysinfo` and `vm_stat` |
| macOS (x86_64) | libSystem | type-checked only: CI's macOS runners are arm64. The FFI layouts are identical on both, but Intel Macs and Rosetta (4 KiB user pages on a 16 KiB kernel) are not exercised |
| FreeBSD and other targets | `sysinfo` | type-checked in CI (cross-check), not run |

### What "used memory" means

Host "used" memory now has one meaning on every platform: memory that
cannot be given to a new allocation without reclaiming or compressing
something. The file cache is not counted.

| Platform | "Used" memory |
|---|---|
| Linux | `MemTotal - MemAvailable` (`/proc/meminfo`) |
| Windows | total minus available physical memory (`GlobalMemoryStatusEx`) |
| macOS | app memory + wired + compressed, Activity Monitor's "Memory Used" |
| other targets (`sysinfo`) | `sysinfo`'s used memory |

On macOS this is lower than 1.x and `sysinfo` reported: they counted every
active page, file cache included, plus speculative pages (on a 14 GB CI
runner, 5.7 GB here against 10.9 GB). Dashboards and health thresholds based
on macOS memory use may need adjusting.

## Known issues

- Concurrent lookups of one series share a shard lock and do not scale
  with cores; hold the handle on hot paths.
- `observe_with_exemplar` drops the exemplar (not the observation) when
  another thread is writing the same bucket's exemplar at that moment, so
  the hot path never waits.
- On targets served by `sysinfo` (FreeBSD and others), a sample still
  scans the process table, and `sysinfo` 0.37+ needs Rust 1.88, so those
  targets stay on 0.36.1. The exporters serve the background monitor's
  cached sample there.
